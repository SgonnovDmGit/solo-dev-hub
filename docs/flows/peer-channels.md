## Зачем понадобилось

Действующие каналы SDH кодируют иерархию **именем папки**: `docs/backend-requirements/` (я клиент, ты мой сервер), `docs/client-requirements/<репо>/` (я сервер, ты мой клиент). Само имя говорит, кто кому должен.

REQ работает не потому, что это удобный формат, а потому, что в нём есть **направление долга**: клиент просит, сервер обязан ответить, потому что владеет услугой. Получатель не может просто сказать «не буду». Именно это делает `declined` редким исключением.

У равных долга нет — никто не владеет дорожной картой соседа. Скопировать REQ один в один нельзя: получится канал, где обе стороны шлют требования, обе вправе отказать и арбитра нет. Два агента будут вежливо уступать по кругу.

Схема обкатана владельцем в `LenSA_Query` на паре «консоль ↔ Ассистент» до того, как стала каноном. Канал востребован не только внутри проекта: сервер↔сервер между продуктами (Lensa ↔ DLemma ↔ DmLab) — та же геометрия.

## Кто кому равный — только явная связь

`peers_of_repo(repo_id)` читает **строки `peer_links` и больше ничего**. Совпадение роли канала не открывает.

Первая версия выводила пары автоматически по совпадающей роли внутри проекта. Владелец забраковал это сразу, увидев результат: шесть тестовых клиентов в одном проекте дали **двадцать** каналов, и все получили право писать всем. Подключение равного — такое же решение, как подключение микросервиса: открываешь те каналы, которые нужны, и никаких других.

Роли при связывании не проверяются: кто кому равный, решает владелец, и пара внутри проекта заводится ровно так же, как пара между продуктами.

Связь симметрична, поэтому в БД нормализуется на записи: `CHECK (repo_a_id < repo_b_id)` + `UNIQUE`. Без нормализации одна логическая пара легла бы двумя строками и синк отработал бы по ней дважды за проход.

**Разрешённые пары видны агенту в `docs/project.md`, секция `## Peer channels`.** Репозитория нет в таблице — значит он не равный, как бы ни совпадала роль, и обмена с ним быть не может.

## Раскладка

```
docs/InOutBox/
├── outbox/<сосед>/     что я отправил соседу        — пишу я
├── inbox/<сосед>/      что сосед отправил мне       — пишет приложение
├── pact/<сосед>/       двусторонние договорённости  — пишут обе стороны
└── registry.md         сквозной реестр номеров      — пишет только агент
```

`<сосед>` — последний сегмент имени репо контрагента (`Repository::canonical_folder_name()`), как и в остальных каналах.

**Имена папок называют направление, а не роль.** Это и есть отличие от иерархических каналов: роли между равными нет, а направление есть всегда.

Вся папка `docs/InOutBox/` — в managed `.gitignore` (как `docs/todo.md` и `docs/codex/`): это рабочий инвентарь переписки, а не история продукта. Авто-коммит её пропускает (gitignored-пути не форс-аддятся), `git status` остаётся чистым.

## Семантика копирования — разная по папкам

| Направление | Как | Почему |
|---|---|---|
| `outbox/<сосед>/` → их `inbox/<я>/` | **зеркало с прунингом** (`mirror_dir`) | инбокс — реплика, обязана следовать за авторской копией, включая удаления |
| `pact/<сосед>/` ↔ их `pact/<я>/` | **объединение без прунинга** | обе стороны кладут файлы в одну папку; зеркало съело бы чужие |

В `pact/` конфликт одинакового имени разводится по времени изменения: выигрывает более свежая копия — это ровно «источник истины у автора», как только автор что-то поправил. Оба репо лежат на одном диске, перекоса часов нет. Одинаковый mtime при разном содержимом приписать автору невозможно — тогда не пишется ничего и пара показывается ошибкой; по правилу «один файл — один писатель» такое состояние означает, что кто-то правил реплику.

Агент **не пишет в `inbox/`** никогда и **не пишет в чужой репозиторий** никогда. Это противоположность вертикальному каналу анонсов, где carve-out прямой записи в чужой репо разрешён явно, — правило не переносится между каналами.

## Единицы обмена

| Род | Где лежит | Ответ |
|---|---|---|
| `PACT-NNN_<slug>.md` | `pact/<сосед>/` | обязателен — `.ack.md` |
| `HANDOFF-NNN_<slug>.md` | `outbox/<сосед>/` | не требуется |
| `NOTE-NNN_<slug>.md` | `outbox/<сосед>/` | не требуется |

Тройка PACT — по образцу REQ и ровно по той же причине, **один файл — один писатель**: `.md` инициатора, `.ack.md` второй стороны, `.impl.md` инициатора. Файл, который правят обе стороны, разъезжается на первом же обмене.

**Строка авторитета в PACT обязательна и объявляется на предмет, а не на репозиторий.** У равных нет умолчания: по общему коду авторитетна консоль, по форме чата Ассистента — Ассистент. Одна пара репо может быть в разных ролях в разных пактах.

Статусы ack: `agreed` / `agreed-with-limits` (оговорки перечислены) / `declined` (**законный ответ**, не сбой) / `clarification-needed`. Два круга уточнений без вердикта — эскалация владельцу; третьего круга не бывает.

## Снос — по маркерам, база вперёд

| Род | Маркер | Кто кладёт | Что сносится |
|---|---|---|---|
| PACT | `<имя>.impl.md` | инициатор | `.md` + `.ack.md` + `.impl.md` |
| HANDOFF / NOTE | `<имя>.done.md` | отправитель | `.md` + `.done.md` |

Снос выполняется **на всех сторонах до любого копирования**. Если удалить только у себя, объединение `pact/` (без прунинга) вернёт файл с реплики соседа на следующем проходе — тот же класс отказа, что воскрешение REQ в v1.9.5. Снос идемпотентен: отсутствующий файл — no-op, поэтому пара, видимая из синков двух проектов, закрывается дважды безвредно.

## Реестр — то, чего нет ни в одном старом канале

Номер обмена жил только в имени файла, а закрытие пары файлы удаляет. Закрыть все пары разом — и правило «максимум + 1» выдаст номер, который у контрагента уже был. Это дефект действующего REQ-канала, вскрытый при проектировании канала равных.

`docs/InOutBox/registry.md` — append-only, восемь полей:

```
- PACT-003 | out | LenSa_Assist1C | общий код: донор консоль | 2026-08-24 | 2026-08-26 | agreed | первый влив, манифест v1
```

`id | направление (out/in) | контрагент | предмет | открыт | закрыт | финальный статус | куда уехал результат`

| Свойство | Как обеспечено |
|---|---|
| приложение его не пишет и не удаляет | ни один путь кода в `peer_channels.rs` его не трогает; даже пустым не создаётся |
| под прунинг не попадает | лежит в корне канала, вне зеркалируемых подпапок |
| номера не переиспользуются | номер записан в момент выдачи, а не в имени файла |

Счётчик — **один на канал в пределах репозитория, сквозной по родам и по направлениям**: максимум берётся по всем строкам файла, включая входящие. Если занят `PACT-001`, первая передача области будет `HANDOFF-002`; если сосед прислал `NOTE-009`, следующий мой номер — `010`. Так номер в канале используется один раз любой из сторон и столкнуться не может; колонка `out`/`in` фиксирует, кто его выдал, а не делит пространство надвое. Счётчик на контрагента дал бы при трёх соседях два разных `PACT-001` в одном репо, и ссылка на номер в коммите перестала бы быть ссылкой.

Тот же механизм заведён и в REQ-каналах (`docs/backend-requirements/registry.md`, `docs/microservice-requirements/registry.md`) — см. `sdh-cross-repo-req-send`. Анонсы исключены сознательно: канал односторонний и терминальный, на номер анонса никто не ссылается, поэтому повтор номера не создаёт двусмысленности, ради которой реестр и заведён.

Цена gitignore названа вслух: **потеря рабочей копии уносит историю обменов вместе с нумерацией**. Ровно та же цена, что у `todo.md`, и принята по той же причине.

## Врезка в синк и видимость

`run_peer_channels(db, project_id)` вызывается в `run_project_sync` после иерархических и codex-проходов, до авто-коммита. Для каждого репо проекта резолвятся его равные, пара синкается один раз за проход (дедуп по нормализованному ключу), результат складывается в общие счётчики: записи → `copied`, прунинг и снос → `migrated`, закрытые обмены → `auto_closed` рядом с REQ-парами.

Видимость — команда `list_peer_channels`: секция «🤝 Каналы равных» в экране синка (однородно с 📚 сводами) и блок связей во вкладке «Связи» проекта, где связь заводится модальным диалогом (выбор своего репо + поиск по всему портфелю, уже связанные помечены) и снимается кнопкой «Развязать». Бейдж `synced` / `pending` считается локальным `dirs_equal`, а не `sync::dirs_in_sync`: последний считает пустой источник несинканным — верно для свода, который ничего не опубликовал, и неверно для канала, где пусто с обеих сторон это нормальное состояние покоя.

## Чего каналом делать нельзя

**Равные не договариваются о том, чем владеет уровень выше.** Нужна правка сервера — каждый шлёт **свой** REQ по своей вертикали; пакт вправе лишь зафиксировать, кто из двоих его шлёт, чтобы заявка не задвоилась. Иначе два клиента согласуют между собой поведение сервера, и сервер узнаёт об этом последним — из двух противоречащих заявок.

**Канал не второй трекер задач.** Пакт закрепляет договорённость, а работа по ней живёт в `docs/todo.md` каждой стороны своей задачей.
