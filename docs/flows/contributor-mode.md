## Суть

Один человек (**главный**, роль `main`) делит репо с помощником (**контрибутором**). У каждого своя копия приложения на своём клоне одного и того же репо на GitHub. Транспорт — сам git: общие файлы едут коммитами, установки между собой не разговаривают, сервер приложению не нужен.

Общие файлы: `docs/todo.md`, `docs/done.md`, `docs/bug-reports.md`, папки REQ, папки анонсов, `docs/InOutBox/`, `docs/server-api/`, `docs/microservice-api/`, `.sdh/`, при `share_specs = on` — вся папка `docs/superpowers/` (T-000243, раздел «Спеки» ниже) и зеркало `docs/codex/` (T-000247, публикует только главный — тот же раздел), и — только у главного — `docs/sdh_skills/`. Остальное (`CLAUDE.md`, `docs/project.md`) остаётся локальным у каждой установки.

## Роли

Роль **выводится, руками не ставится**, и кешируется на репо в `repositories.shared_role` (см. [repositories](../schema/repositories.md)):

| Роль | Когда | Что коммитит |
|---|---|---|
| `main` | главный включил общий режим (`repositories.shared_mode`), и логин GitHub этой установки — владелец репо | общие файлы и `.sdh/` — в свою дев-ветку и во все ветки участников |
| `contributor` | `.sdh/project.json` доверенный и в `participants` есть логин этой установки | общие файлы — в свою ветку и в дев-ветку главного |
| `pending` | файл доверенный, но этой установки в нём нет: заявка ждёт подтверждения | только `.sdh/requests/<login>.json` |
| нет | файла структуры нет | ничего особенного: репо обычный |

Логин установки хранится в настройке `github_login` при проверке токена. Без него общее не обрабатывается (`shared_no_login`).

## Структура и заявки

`.sdh/project.json` (format 1): проект (`name`, `type`), главный (`login`, `dev_branch`), репо с ролями (и флагом `share_specs` каждого репо — T-000243, см. ниже), подключённые микросервисы и `participants` (`login`, `branch`, `band_start`). Пишет его только установка главного — при каждом синке.

Помощник просит доступ файлом `.sdh/requests/<login>.json` (`login`, `branch`). Его установка плумбингом кладёт только этот файл в дев-ветку главного и пушит. Главный подтверждает в табе «Участники» (`approve_join_request`): участник появляется в структуре с полосой номеров, файл заявки удаляется коммитом главного, а помощник на своём следующем синке становится `contributor`. Кнопки «Отклонить» в этом релизе нет.

## Спеки: `docs/superpowers/` (T-000243)

`docs/superpowers/` (спеки, планы, мокапы) — локальный агентский workspace; в общем режиме папка передаётся, только если для репо включён флаг **`share_specs`** (колонка `repositories.share_specs`, по умолчанию on — см. [repositories](../schema/repositories.md)). Это решение владельца по каждому репо отдельно: чекбокс «Делиться спеками и планами (docs/superpowers/)» рядом с переключателем общего режима в шапке репо, виден и меняется только главным (владельцем репо или проверенным администратором — тот же доверительный тест, что и у включения режима, проверяется и на бэкенде). Флаг не зависит от `shared_mode` и задаётся **до** включения общего режима — тогда первый же синк не закоммитит спеки; отдельно включать режим, синкать и выключать не нужно.

Свою политику главный публикует в доверенной `.sdh/project.json` — `share_specs` в записи этого репо (легаси-структура без поля = on; неверный тип — включая явный `null` — ошибка доверия, не fallback on). Контрибутор и ожидающий помощник принимают флаг из той же проверенной структуры — до рендера `.gitignore` и вычисления путей — и только для этого репо, не на весь проект; наличие папки или ignore-правил как источник флага не используется. Изменение флага уезжает тем же коммитом структуры при ближайшем синке; смена посреди синка не оставляет старое on в отложенной фазе B — эффективное значение пересчитывается заново на каждом применении.

**On:** managed-`.gitignore` перестаёт игнорировать папку (managed-правило `docs/superpowers/` убирается), папка входит в pathspec обеих ролей симметрично — главный коммитит её, контрибутор получает и может добавить свои спеки (новые файлы с двух сторон сохраняются, обычный merge без драйвера). `docs/sdh_skills/` остаётся только у главного. Preflight включает папку в `probe_paths` и диагностирует пользовательские ignore-правила, мешающие передаче.

**Off:** `docs/superpowers/` исключается из новых коммитов синка — pathspec фаз A/B, плумбинг во все ветки участников, — а управляемый рендер гарантирует ignore папки даже с кастомным или пустым шаблоном. Уже закоммиченные спеки остаются под трекингом с историей: `git rm --cached`, переписывание истории и отмена старых коммитов флагом не делаются; чтобы спеки не попали в репо вообще, флаг должен быть off до их первого коммита любым способом (включая первый общий синк). Обычные git-коммиты, full-branch fetch/fast-forward/merge и уже созданные, но ещё не отправленные коммиты флагом не фильтруются. `pending` при любом флаге отправляет только свою заявку. todo/done/bug-reports едут всегда — флаг покрывает только `docs/superpowers/`.

**Границы, добавленные ревью (T-000243).** Смена флага сериализована с политически-чувствительными шагами синка per-repo (`specs_policy_guard`): setter (`set_repo_share_specs`, IPC с другого потока; команда объявлена `async`, поэтому ожидание guard-а не замораживает UI), фаза B (публикация структуры, pathspec-коммиты, пуш), **оба** рендера `.gitignore` (guard держится через саму запись файла, а не только через чтение политики) и каждый другой писатель структуры — `enable_shared_mode`, `approve_join_request` и `disable_shared_mode` (он коммитит удаление `.sdh/`) — никогда не чередуются: либо вся секция фазы B завершается со старым флагом и ожидающий применяется после, либо ожидающий проходит первым и синк видит новый. Setter, кроме того, отказывает по **роли** раньше, чем по полномочиям: даже проверенный администратор организации не меняет политику репо, где эта установка — контрибутор или ожидающий. Структура, которая есть, но не читается (битый JSON, неверный тип поля — включая явный `null`, — недоверенный источник) или не проходит проверку доверия, — не fallback ни на «on», ни на старую валидную копию из рабочего дерева: discovery отдаёт `shared_untrusted`, эффективная политика — ошибку, и рендер `.gitignore` / коммиты этого репо в этом проходе блокируются с issue (refusal доносится до рендера той же синхронизацией, отдельная кнопка init-docs проходит то же discovery). И наконец, для уже включённого репо с эффективным on повторяющийся синк **диагностирует** пользовательские ignore-правила, глушащие `docs/superpowers/` (перечисление синка уважает `.gitignore`, поэтому без диагностики спеки молча не уезжали бы); правила не удаляются автоматически — только через подтверждение preflight. Включение флага ON у уже расшаренного репо с такими правилами возвращает предупреждение из setter. В UI чекбокс спеков и переключатель общего режима — одно семейство действий: пока сохранение спеков (включая проверку администратора) в полёте или значение ещё не загружено, включение режима не начинается (save-before-enable).

**Кодекс: `docs/codex/` (T-000247).** Тот же флаг `share_specs` управляет и папкой `docs/codex/` — зеркалом подключённых сводов (см. [codex-broadcast.md](./codex-broadcast.md)): при `on` managed-`.gitignore` отпускает и её, при `off` — игнорирует снова. Отличие от спек — публикует её **только главный**: `docs/codex` входит в pathspec лишь роли `main` (как `docs/sdh_skills/`), контрибутор получает зеркало по ветке, но в свои коммиты его не включает. Перед каждой публикацией корень `docs/codex/` проходит подготовку (`prepare_codex_root` в codex.rs): записи вне полного набора подключённых сводов выметаются, а при любой ошибке подготовки codex исключается из путей коммита с диагностикой — постороннее в общий коммит не попадает, остальные общие файлы синкаются. Свип после broadcast (`sweep_codex_inbox`) — только там, где набор имён разрешается полностью: у контрибутора подключений к сводам нет, свип отказывается и доставленное зеркало не трогает.

## Якорь доверия и пин

Файл приходит из репо, куда может писать и помощник, поэтому он доверенный, только если `main.login` — **владелец репо на GitHub** или **его администратор по GitHub API** (`validate_structure` → `main_is_trusted`). Помощник не может сделать себя главным, закоммитив свой `project.json`.

Первая принятая структура пинит дев-ветку главного (`pin_after_accept`, в `shared_import`). С этого момента смотрится только `origin/<пин>`, а структура с другой дев-веткой — `shared_untrusted`. Две структуры-кандидата на разных ссылках тоже недоверенные: ни одна не выбирается. Выключение главным тоже читается с пиненой ветки: если на её кончике файла больше нет, репо снова обычный, что бы ни хранила собственная ветка контрибутора.

**Репо организаций (T-000227).** Владелец такого репо — организация, поэтому сравнения логинов мало. Права проверяет JS (`isRepoAdmin`: `GET /repos/{owner}/{repo}/collaborators/{login}/permission`, `permission === "admin"`) и пишет ответ командой `set_shared_admin_verified` в настройку `shared_admin_verified` (`{repo в нижнем регистре: {login, admin, checked_at}}`, см. [settings](../schema/settings.md)). Rust в GitHub не ходит: он доверяет записи, только если логин совпадает и `admin = true`. Каждый синк и проба возвращают `admin_checks` — общие репо, где `main.login` не владелец, — и `sync-core.ts` перепроверяет их все; если какая-то проверка впервые дала admin, синк повторяется один раз. Отзыв admin действует со следующего синка с сетью; ошибка запроса (нет токена, 403/404, сеть) ничего не пишет. Включить режим может владелец или проверенный администратор; переключатель показывается владельцу и тем, у кого по последнему списку репо есть `permissions.admin` (настройка `github_admin_repos`).

## Один синк: фаза A, потом фаза B

`run_project_sync_in` проводит общий путь вокруг обычных шагов.

**Фаза A** (`run_phase_a`, до любых записей) — для каждого общего репо синкаемого проекта, плюс троттлинговый пробинг (раз в 10 минут) репо портфеля без роли:
1. зарегистрировать драйвер слияния в `.git/config` клона (идемпотентно, на каждом синке);
2. `git fetch origin` (системные учётные данные git, токен git не передаётся);
3. определить роль по структуре и логину;
4. fast-forward веток-получателей: текущей — `git merge --ff-only` (только если ни один общий файл в рабочем дереве не изменён), остальных — `update-ref` со старым значением как compare-and-swap. Разошлись — статус `needs_manual_merge`, никогда не force;
5. **импорт** пришедшего коммитом (ниже);
6. только контрибутор: взять канон правил главного (ниже).

**Обычные шаги** — скелеты файлов, копирование REQ, кодекс, каналы между равными — см. остальные flow.

**Фаза B** (`SharedSync::finish`): записать структуру или заявку, закоммитить общие файлы в текущую ветку (pathspec-коммит) и в остальные ветки-получатели (плумбинг, пофайловое трёхстороннее слияние по id), `git push` веток-получателей одной командой без `--force`, выставить статус. `master` и `main` отказываются на каждом слое (`git_sync`), а хук на удалённой стороне в e2e-тестах фиксирует любое их обновление и любое не-fast-forward обновление.

## Слияние по id

`todo.md`, `done.md` и `bug-reports.md` сливаются по сущностям, не как текст: одна и та же функция обслуживает драйвер слияния git (`merge=sdh` в `.gitattributes`, исполняемый файл запускается как `app --merge-driver %O %A %B %P`) и плумбинг-коммит в ветку, которая не checked out. Для трёх версий строки с id:

- есть только с одной стороны — добавляется;
- удалена с одной стороны и не изменена с другой — удаляется; удалена с одной и изменена с другой — остаётся изменённая;
- поле изменено только с одной стороны — берётся это изменение;
- поле изменено с обеих сторон по-разному: **статус** уходит к тому, что дальше по ходу работы (задача `open < in-progress < review`, строка в `done.md` побеждает строку в `todo.md`; баг `created < in-progress < testing`, `rejected` после `testing`), любое другое поле — к стороне, которая сливает (`%A`). Маркера конфликта не бывает никогда.

Нераспознанная строка берётся дословно из `%A`. База плумбинг-слияния выбирается по каждой сущности отдельно (T-000226): последнее состояние этой строки (версия или отсутствие), общее для обеих историй, — последний элемент наибольшей общей подпоследовательности историй, спроецированных на строку (история — до 200 коммитов файла). Файл целиком по возрасту первого появления остаётся базой только для структуры (заголовки, проза) и для строки, которой не было в общих состояниях. Драйвер слияния git (`merge_driver`) берёт собственную базу git и этого не использует.

## Импорт как правда

Пришедшее коммитом — правда, БД идёт следом (`import_incoming`). В `repositories.shared_import` хранится, по каждому общему файлу, blob, импортированный или закоммиченный этой установкой последним. Если blob в HEAD отличается, разница «сохранённое → HEAD» применяется к БД: защищённые поля багов и новые строки включены, автор пишется в `task_events.author` / `bug_events.author` (см. [task_events](../schema/task_events.md), [bug_events](../schema/bug_events.md)) — это логин из трейлера `SDH-Participant:` коммитов, иначе владелец полосы id. Затем рабочее дерево сверяется как обычно: незакоммиченная локальная правка защищённого поля восстанавливается, закоммиченная остаётся. Первый синк репо — базовая линия, ничего не применяет.

## Полосы номеров

Две установки не должны выдать один id. У главного — всё ниже первой полосы участников; участник получает `500000 + k * 100000`, `k = 0..4` (до пяти участников), одна полоса на все префиксы (`T`, `F`, `O`, `M`, `B`); номер берётся как максимум внутри полосы (`band_for`, `next_numeric_id_in_band`). Ожидающий помощник номера выдавать не может. Полоса каждой установки записывается в секцию CLAUDE.md общего репо шестью цифрами без разделителей (например, `500000`–`599999`; у главного `000001`–`499999`).

## Статусы

`repositories.shared_status`, показываются в шапке репо и значком в сайдбаре; тост — только когда статус появился, не на каждом синке. Порядок объявления `SharedStatus` — приоритет, если применимо несколько:

`shared_untrusted` > `fetch_failed` > `push_failed` > `push_rejected` (защищённая ветка, `GH006`) > `needs_manual_merge` (даёт кнопку «Слить»: `git merge origin/<ветка>` с драйвером, при конфликте в коде — отмена) > `no_own_branch` > `pending_approval`. `shared_no_login` бывает только в одиночку.

## Видно ли, что участник синкает (T-000237)

- **У главного** вкладка «Участники» показывает «Последняя отправка» (`shared_participants_activity`): самый свежий коммит установки участника — трейлер `SDH-Participant: <login>` — среди последних 200 коммитов `origin/<его ветка>` и `origin/<дев главного>`, без fetch. Синк, которому нечего было отправить, следа не оставляет; ручные коммиты участника сюда не входят.
- **У контрибутора и ожидающего помощника** в шапке репо постоянная строка «Автосинк выключен…», пока таймер этот репо не синкает: выключен общий переключатель, или флаг проекта, или репо без проекта (`autoSyncOffHint`). Кнопка «Включить» ставит оба флага; у репо без проекта — только текст.
- Синк одного репо с его экрана — кнопка «🔄 Синк» (`sync-run.ts`): репо в проекте синкает проект, репо без проекта — проба общего режима, как в сайдбаре.

## Правила: канон главного

Копии правил в `docs/sdh_skills/` общего репо — главного.

- **Главный:** рендерит как в любом репо и коммитит их (маркеры `*.approved` и файлы причин `*.conflict` из pathspec исключены).
- **Контрибутор и ожидающий помощник:** `skips_rule_copies` истинно. Установка ничего не рендерит в `docs/sdh_skills/` этого репо, ничего не чистит и маркеры возврата оттуда не собирает. Копии, которые прежняя версия отрендерила туда без трекинга, удаляются, когда роль определена и она не `main` (`drop_untracked_rule_copies`: файлы `sdh-*.md`, которые git не трекает): git отказывается делать fast-forward поверх неотслеживаемых файлов, которые пришедший коммит создаёт.
- **Канон.** После импорта `adopt_main_canon` читает копии `docs/sdh_skills/<name>.md` с **`origin/<дев-ветка главного>`** — опубликованной ветки главного, той же границы доверия, что и файл структуры; собственная ветка контрибутора, в которую он пишет сам, не читается, а нет ссылки (ещё не было fetch) — проход пропускается. Каждое правило, чьё имя установка знает и чья копия есть на этой ветке, **запоминается как следуемое** — независимо от того, совпадает ли текст. Если текст отличается от канона установки, он записывается как её собственный кастомный канон (`templates`, `_global`, `skill.<name>.md.tmpl`), в [rule_events](../schema/rule_events.md) пишется событие `taken` с заметкой `canon of main <login>`, и синк рендерит всё везде, так что остальные репо контрибутора и `~/.claude/skills` получают тот же текст. Если два общих репо несут разный текст одного правила, побеждает и остаётся копия с самым свежим коммитом, который её касался.
- **Замок.** Следуемое правило хранится в настройке `rules_from_main` (правило → логин, репо, время коммита), см. [settings](../schema/settings.md). Экран «Правила» помечает его «канон главного» и отключает «Сохранить» и «Сбросить»; бэкенд отказывает ошибкой `rule_follows_main: <login>`; маркер возврата такого правила в обычном репо откладывается как superseded. Чтобы изменить правило, контрибутор просит главного. Подсказка на экране: «Это правило правит главный ({login}). Хотите изменить — попросите его.»
- **Снятие замка.** Запись действует, только пока её репо — репо контрибутора этой установки. Когда роль очищена или репо удалён, запись сбрасывается при следующем чтении, и правило снова редактируемое; его текст остаётся кастомным каноном установки. Если репо снова стало общим, следующий проход записывает замок заново.
- **Предложения правок (T-000241, v1.23.0).** Маркер возврата `*.approved` в общем репо контрибутора больше не откладывается, а становится предложением: применяется у контрибутора сразу, едет к главному файлом `.sdh/rule-proposals/`, решение возвращается неизменяемой квитанцией `.sdh/rule-decisions/`. Машины состояний, CAS, публикация и GC — [rule-proposals.md](./rule-proposals.md).

## Клон репо без локальной папки (F-000045)

Кнопка «🔄 Синк» на экране репо без `local_path` (и с `github_name` вида `owner/repo`) не молчит, а предлагает клон: confirm-диалог → системный выбор папки → команда `clone_repo_to(id, targetDir)` → привязка `local_path` → обычный синк по `chooseSyncAction` (проектный синк или проба общего режима — клон сам по себе shared-режим не включает и роли не меняет). Пикер выбирает сам корень клона. Цель: несуществующая или пустая папка — `git clone`; уже существующий клон того же репо (точное совпадение fetch-URL `origin` с `github_name`, без учёта регистра, HTTPS/SSH, необязательный `.git`) — просто привязка, ничего не трогается; чужой репозиторий, непустая не-git папка, файл, вложенная папка чужого рабочего дерева — отказ без единой записи. Ветка после clone — настроенная `autocommit_branch`, иначе `dev`; если `refs/remotes/origin/<ветка>` нет, checkout пропускается и остаётся HEAD/ветка, выбранные клоном (не ошибка, ветка не создаётся). Привязка атомарна (`bind_repo_local_path_if_unset`): конкурентное ручное присоединение не перезаписывается. Ошибки — `SyncIssue` с кодами `clone_target_invalid` / `clone_failed` / `clone_attach_failed`, показываются через `formatSyncIssues`; при неудаче папка не привязывается. Неудачная попытка оставляет маркер `.sdh-clone-incomplete-<hash>` рядом с целью (вне клона): повторный запуск по той же папке отклоняется, пока пользователь не уберёт остатки и маркер вручную — частичный клон никогда не привязывается как готовый. Портфельный синк в сайдбаре clone не предлагает — только кнопка на экране репо.

## Выключение

Главный выключает режим (`disable_shared_mode`): `.sdh/` удаляется коммитом на его дев-ветке и на каждой ветке участника, управляемые блоки `.gitignore` / `.gitattributes` возвращаются к обычному виду, а уже закоммиченные файлы остаются под трекингом (существующий диалог «снять с трекинга файлы, попавшие под .gitignore» предлагает `git rm --cached`). Следующий синк контрибутора не находит структуры на пиненой ветке, очищает свою роль и статус, удаляет устаревший `.sdh/` со своей ветки и пушит; репо снова обычный, локальная БД не чистится. Удаление, не дошедшее до remote, повторяется на следующих синках.
